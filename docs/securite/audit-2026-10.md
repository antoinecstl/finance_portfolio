# Audit de sécurité technique — Fi-Hub (octobre 2026)

Branche des correctifs : `claude/audit-securite`. Base : `master` au commit `2dc1839`.

## Résumé

Le socle est sain : authentification revérifiée côté serveur sur chaque route, protection CSRF par contrôle d'origine sur toutes les mutations par cookie, isolation des données dans Postgres (RLS et fonctions qui vérifient `auth.uid()`), webhook Paddle signé, serveur OAuth 2.1 correctement construit (PKCE S256, codes à usage unique, jetons hachés), aucun secret dans l'historique git.

Le risque principal était **la version de Next.js** (16.1.0), concernée par une quarantaine d'alertes publiées, dont plusieurs critiques. Viennent ensuite des points de logique métier : le webhook de paiement faisait confiance à un identifiant fourni par le navigateur, la limite de l'import IA était contournable, et la suppression d'un compte laissait son abonnement facturé.

Tous les points marqués **Corrigé** sont traités dans la branche, avec tests. Les points **À faire** relèvent de réglages dans Supabase, Vercel ou Paddle, ou de chantiers plus longs.

## Périmètre et méthode

- Lecture du code : 39 routes API, proxy d'authentification, pages protégées, admin, OAuth/MCP, import, webhook, fonction Edge.
- Base : 33 migrations Supabase, politiques RLS, fonctions `SECURITY DEFINER` et leurs droits d'exécution.
- Dépendances : `npm audit` (production et développement).
- Historique git : recherche de secrets (clés OpenAI, Supabase, Paddle, Resend, webhooks Slack/Discord) sur tous les commits.

**Non couvert :** la configuration réelle des consoles Supabase, Vercel et Paddle (je n'y ai pas accès), et aucun test d'intrusion sur la production. Les politiques RLS sont auditées d'après les migrations ; la requête de contrôle en fin de document vérifie que la base de production y correspond.

## Constats détaillés

### 1. Next.js 16.1.0 vulnérable — Critique — Corrigé

`npm audit` remontait une quarantaine d'avis sur `next@16.1.0`, dont :
- exécution de code à distance via l'optimiseur d'images (AVIF) ;
- SSRF via l'optimiseur d'images ;
- contournements du middleware ou proxy (routes de prefetch, paramètres dynamiques) ;
- empoisonnement de cache entre utilisateurs ;
- plusieurs dénis de service.

**Impact atténué :** les pages connectées revérifient la session côté serveur (`app/(app)/layout.tsx`) et chaque route API appelle `auth.getUser()`, donc un contournement du middleware ne suffisait pas à lire des données.

**Correctif :** `next` et `eslint-config-next` en `16.4.0`. Le build, les tests et un parcours réel dans le navigateur passent.

Next 16.4 signale que la convention `middleware.ts` est dépréciée au profit de `proxy.ts`. Ce n'est pas bloquant ; le renommage se fera à part (`npx @next/codemod middleware-to-proxy`).

### 2. Dépendances transitives — Élevée — Corrigé

`npm audit fix` a mis à jour `ws`, `sharp`, `postcss`, `dompurify` (via jsPDF), `fflate`, `tmp`, `nanoid`, `brace-expansion`, `minimatch`, `source-map-js` et `baseline-browser-mapping`.

- **`uuid` :** utilisé par `exceljs`, il est forcé en `^11.1.1` par `overrides` (l'import Excel a été vérifié).
- **Vitest :** passage de 2.1.9 à 4.1.11 (avis critiques sur le serveur de l'interface de test), avec `vite@7` en dépendance de développement. `@vitest/ui`, inutilisée par les scripts, est retirée. Vitest 5 a été écarté : il exige Node 22.12 ou plus, alors que la CI tourne sur Node 20.

**Reste une alerte :** `braces`, via `@next/eslint-plugin-next`. C'est un déni de service dans l'outillage de lint, jamais livré en production, et aucun correctif n'existe encore.

**Effet secondaire :** `eslint-plugin-react-hooks` 7.1 durcit la règle `set-state-in-effect`, ce qui fait 16 occurrences dans du code existant. Elle est passée en avertissement dans `eslint.config.mjs` pour ne pas bloquer la CI, et sera à migrer à part.

### 3. Webhook Paddle — Moyenne — Corrigé

**Faille :** le webhook rattache un abonnement à un utilisateur via `custom_data.user_id`, une valeur posée par le navigateur au moment du checkout (`BillingActions.tsx`), donc modifiable.

**Scénario :** un tiers qui connaît l'identifiant d'un abonné ouvre un checkout avec cet identifiant (le premier mois est gratuit), puis résilie. Le webhook `subscription.canceled` repassait l'abonné en Free, et `subscription.created` écrasait son abonnement.

**Correctif** (`app/api/webhooks/paddle/route.ts`) :
- un abonnement en cours n'est plus remplacé par celui d'un autre client Paddle ;
- une résiliation ne touche que l'abonnement Paddle nommé dans l'événement.

La signature (HMAC, comparaison en temps constant, fenêtre anti-rejeu de 5 minutes) et l'idempotence étaient déjà correctes.

### 4. Limite de l'import IA contournable — Moyenne — Corrigé

**Faille :** `/api/import/parse` déclenche des appels OCR (Mistral) et LLM (OpenAI) facturés. Sa limite de 20 analyses par heure était tenue en mémoire, par instance serverless : en parallélisant les requêtes, on la multiplie par le nombre d'instances. L'accès est réservé aux comptes Pro, mais un seul compte suffit à faire grimper la facture.

**Correctif :** nouveau `lib/shared-rate-limit.ts`, qui s'appuie sur le compteur Postgres déjà utilisé par l'API publique (`api_rate_limit_hit`). Si la base ne répond pas, il retombe sur la limite en mémoire. L'en-tête `Retry-After` est renvoyé.

### 5. Suppression de compte sans résiliation — Moyenne — Corrigé

**Faille :** `/api/account/delete` supprimait l'utilisateur sans toucher à son abonnement Paddle. Le client continuait d'être prélevé pour un compte qui n'existe plus, ce qui pose un problème de droit de la consommation.

**Correctif :**
- l'abonnement facturé est résilié immédiatement via l'API Paddle avant la suppression ;
- si la résiliation échoue, rien n'est supprimé et l'utilisateur reçoit un message clair (affiché par `DangerZone.tsx`).

### 6. Hameçonnage par le consentement OAuth — Moyenne — Atténué

**Risque :** l'enregistrement dynamique de clients (nécessaire pour ChatGPT et Claude) est ouvert, et le nom de l'application est déclaré par l'application elle-même. Un attaquant peut enregistrer un client « ChatGPT » qui redirige vers son domaine, puis envoyer le lien d'autorisation à une victime. PKCE ne protège pas ce cas, puisque l'attaquant a créé lui-même le défi.

**Atténuation faite :** l'écran de consentement affiche désormais un avertissement « Application non reconnue » quand l'adresse de retour n'est pas celle d'un assistant connu (chatgpt.com, claude.ai, claude.com, localhost). Le domaine de redirection était déjà affiché.

**À faire (option) :**
- limiter la durée de vie des clients jamais utilisés ;
- journaliser chaque nouveau consentement et prévenir l'utilisateur par e-mail.

### 7. Authentification — Moyenne — À faire (console Supabase)

- **Vérification du mot de passe actuel :** elle est faite côté navigateur (`ChangePasswordForm.tsx`). Avec une session volée, `updateUser({ password })` fonctionne sans elle. Activer **Secure password change** (réauthentification) dans Supabase → Authentication.
- **Mots de passe compromis :** activer **Leaked password protection** (vérification HaveIBeenPwned).
- **Longueur minimale :** la règle des 8 caractères est vérifiée côté client seulement. Fixer **Minimum password length** à 8 ou plus dans Supabase.
- **Robots :** ajouter un CAPTCHA (Cloudflare Turnstile, intégré à Supabase) sur l'inscription et la connexion, contre le bourrage d'identifiants.
- **MFA :** proposer la double authentification (TOTP, intégrée à Supabase), au minimum obligatoire pour le compte admin. Ce sont des données patrimoniales.
- **Confirmation d'e-mail :** vérifier qu'elle est activée.

### 8. Fonction SQL interne appelable par tous — Faible — Corrigé (à appliquer)

**Faille :** `assert_account_sequence_valid(p_user_id, p_account_id)` est `SECURITY DEFINER` et accepte n'importe quel `user_id`. Sur Supabase, les fonctions du schéma `public` sont exécutables par `anon` et `authenticated` par défaut. Quelqu'un qui connaît deux identifiants pouvait l'appeler en RPC et lire, dans le message d'erreur, un symbole et une date d'un autre compte si son historique est incohérent.

**Correctif :** migration `20261012_revoke_internal_functions.sql`, qui retire le droit d'exécution aux rôles de l'API. Ses appelants légitimes sont des fonctions `SECURITY DEFINER` et ne sont pas affectés.

**À appliquer** sur la base de production (éditeur SQL Supabase ou `supabase db push`).

Toutes les autres fonctions exposées (`insert_transaction_with_fee`, `update_transaction_with_fee`, `insert_transactions_batch`, `delete_transaction`) vérifient bien `auth.uid()` et la propriété du compte. Le drapeau `is_founder` est protégé par un déclencheur, et les tables `subscriptions`, `webhook_events`, `admin_tickets`, `api_tokens` et `oauth_*` ne sont pas modifiables par les utilisateurs.

### 9. Erreurs internes renvoyées au navigateur — Faible — Corrigé

- **Import :** l'erreur pouvait contenir jusqu'à 500 caractères de la réponse du fournisseur OCR, ou un message de configuration (« OPENAI_API_KEY manquant… »). L'utilisateur reçoit maintenant un message générique ; le détail reste dans les journaux serveur.
- **Portail de facturation :** même traitement pour les erreurs Paddle.

### 10. Accès admin — Faible — Corrigé

**Faille :** l'admin est reconnu par son adresse e-mail (`ADMIN_EMAILS`, avec ton adresse par défaut), sans vérifier que l'adresse est confirmée.

**Correctif :** `email_confirmed_at` est désormais exigé.

**À faire :** définir `ADMIN_EMAILS` explicitement sur Vercel, et à terme porter le rôle dans `app_metadata`, que seul le serveur peut écrire. Activer la MFA sur ce compte (voir point 7).

### 11. Fonction Edge d'alerte d'inscription — Faible

- **Comparaison du secret :** elle se fait désormais en temps constant. Corrigé.
- **Canal ntfy (à vérifier) :** le serveur par défaut est `ntfy.sh`, qui est public, et le message contient l'e-mail du nouvel inscrit. Si `SIGNUP_NTFY_TOPIC` est un nom devinable, n'importe qui peut s'abonner et lire les inscriptions, ce qui est une fuite de données personnelles. Utiliser un sujet aléatoire long avec un jeton d'accès (`SIGNUP_NTFY_TOKEN`), ou désactiver ntfy.

### 12. Politique de sécurité du contenu (CSP) — Faible — À faire

`script-src 'unsafe-inline'` affaiblit la protection contre le XSS, et `connect-src https: wss:` autorise n'importe quel domaine. Pistes :
1. restreindre `connect-src` au projet Supabase, à Paddle et aux domaines Vercel ;
2. passer `script-src` en nonces : Next les gère via le proxy, et ça demande un rendu dynamique des pages.

Aucun point d'injection HTML n'a été trouvé dans le code applicatif. Seuls deux blocs JSON-LD statiques sont injectés, et ils sont désormais échappés.

### 13. Divers — Info — Corrigé

- **JSON-LD :** `<` est désormais échappé dans les données structurées, par défense en profondeur.
- **Limiteur en mémoire :** les routes cours, historique, recherche et change partageaient la même clé de limite, si bien qu'un tableau de bord chargé pouvait recevoir des 429 sur l'historique. Chaque route a maintenant sa propre clé.

## Ce qui est déjà bien fait

- **CSRF :** contrôle d'origine sur toutes les mutations authentifiées par cookie (`lib/api-security.ts`), plus `Content-Type` JSON et taille maximale des corps.
- **Redirections :** les redirections après connexion sont filtrées (`safeInternalRedirect`), sans redirection ouverte.
- **Données :** isolation dans Postgres (RLS et fonctions qui vérifient le propriétaire). L'API publique ne fait jamais confiance à un `user_id` venant de l'application.
- **Jetons et OAuth :** seuls des hachages SHA-256 sont stockés ; codes à usage unique avec expiration ; PKCE S256 obligatoire ; rotation des jetons de rafraîchissement.
- **Webhook Paddle :** signé, avec comparaison en temps constant, anti-rejeu et idempotence.
- **En-têtes HTTP :** HSTS, `X-Frame-Options`, `frame-ancestors`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`.
- **Secrets :** `.env*` est ignoré par git et aucun secret ne figure dans l'historique.

## À faire de ton côté

1. **Fusionner la branche et déployer.** C'est le point le plus urgent, à cause de Next.js.
2. **Appliquer la migration** `supabase/migrations/20261012_revoke_internal_functions.sql`.
3. **Supabase → Authentication :**
   - activer Secure password change et Leaked password protection ;
   - fixer la longueur minimale à 8 ou plus ;
   - vérifier que la confirmation d'e-mail est active ;
   - ajouter un CAPTCHA ;
   - activer la MFA sur le compte admin.
4. **Vercel :**
   - définir `ADMIN_EMAILS` ;
   - activer Deployment Protection sur les previews, qui sont publiques et utilisent les mêmes secrets ;
   - activer le pare-feu (règle de limite de débit sur `/api/*`).
5. **ntfy :** vérifier le sujet et ajouter un jeton (point 11).
6. **Supabase :** vérifier que les sauvegardes et le PITR sont actifs.
7. **CI :** ajouter `npm audit --omit=dev --audit-level=high` et Dependabot, pour ne plus rester sur une version vulnérable sans le savoir.

### Contrôle de la base de production

À lancer dans l'éditeur SQL de Supabase. Le résultat attendu : toutes les tables ont `rowsecurity = true`, et aucune fonction `SECURITY DEFINER` acceptant un identifiant d'utilisateur n'est exécutable par `anon` ou `authenticated`. Deux exceptions sont normales : les fonctions de déclencheur, qu'on ne peut pas appeler directement, et `user_has_pro_access`, nécessaire aux politiques RLS (elle ne révèle que le statut Pro d'un identifiant).

```sql
select tablename, rowsecurity from pg_tables where schemaname = 'public' order by 1;

select p.proname,
       pg_get_function_identity_arguments(p.oid) as args,
       has_function_privilege('anon', p.oid, 'execute') as anon_exec,
       has_function_privilege('authenticated', p.oid, 'execute') as auth_exec
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.prosecdef
order by 1;
```
